# 性能

[English](../en/performance.md) | **简体中文**

> 复现命令：`mvn -q -DskipTests package && bash scripts/bench.sh`
> 报告里每个数字都能用这条命令重新测出来，没有靠形容词解释的例外。

- 实测时间：2026-10
- 机器：Debian 13 · x86_64 · 4 核 · 7.9 GB 内存（虚拟机）
- 运行时：JDK 17（G1，默认堆）
- 被测形态：Spring Boot starter + H2 + 真实事务（`harken-demo` 可执行 jar）

---

## 1. 端到端延迟

每次都是 `POST /harken/api/execute` 走完整链路：HTTP → 会话校验 → 同源校验 →
Groovy 编译（或命中缓存）→ 事务 → 结果序列化。

| 场景 | 平均耗时 | 说明 |
|---|---|---|
| **首次执行**（冷 JVM，含 Groovy 初始化） | **73 ms** | 第 1 次；第 2、3 次已降到 19 ms |
| **同一脚本重复 50 次**（命中编译缓存） | **4.1 ms** | 日常使用的主路径 |
| **每次都是新脚本 30 次**（必然重新编译） | **15.4 ms** | 最坏情况：AI 每次都写新脚本 |

怎么读这三个数：

- **4.1 ms 和 15.4 ms 的差距就是编译缓存带来的收益。** 缓存按源码 SHA-256 命中，LRU 128 条。
- **73 ms 是第一次点执行时的体感。** 它实际不是 4 ms 的十八倍，大头是 Groovy 自己的
  类初始化，进程活着就只付一次。
- 这些数字包含 HTTP 与序列化。单独测 Groovy 编译会更快，但用户感受到的是端到端，
  所以不做微基准。

## 2. 内存

| 指标 | 实测 |
|---|---|
| Metaspace（启动后、跑基准前） | 49.5 MB |
| 跑 500 个不同脚本后 | 55.0 MB（**+5.5 MB**） |
| 再跑 500 个不同脚本后 | 57.0 MB（**+2.0 MB**） |
| 堆（G1，used） | 约 76 MB / 总 120–165 MB |
| 单进程常驻 | 约 350 MB RSS |

**结论：Metaspace 是收敛的，不是线性泄漏。**

第一批 +5.5 MB、第二批只有 +2.0 MB（约第一批的 36%）。原因有两层：

1. 编译缓存 LRU 128 条，超出后旧 `Script` 对象被丢弃；
2. 被丢弃的类和它的 `ClassLoader` 一起变得不可达，Metaspace 在一次 Full GC 后回收。

但**不能说它永远不会涨**：如果负载持续是每秒都有全新脚本，短期内仍会看到爬升，
直到 GC 跟上。缓解手段是限制 `max-script-length`、优先用受限模式的固定目录、必要时定期重启。

> 这个结论是加测了第二批之后才定下来的。最初只测一批 500 个，看到 +5.5 MB 会以为是线性
> 增长，准备写成「需定期重启」；第二批只涨 2.0 MB，才看出是收敛的。

## 3. 补全元数据

| 指标 | 实测 |
|---|---|
| 全量索引（demo 的 bean 数量下，未压缩） | 1.3 KB |
| 全量索引耗时 | 1–4 ms |
| 单个 Bean 的方法表（首次） | 2 ms 左右 |
| 同一方法表（命中前端缓存） | 0 ms，不出网 |

生产应用里 bean 可能上百个、类上千个，索引会到几十 KB，所以生产环境建议开 gzip
（实测 `codemirror.js` 402 KB → 107 KB，-73%；索引是同类文本，压缩率接近）。

方法表按需拉：敲点号时只问一个名字，不是一次拖回来全站所有方法。

## 4. 相比不用 Harken 多了什么

Harken 增加的成本主要是两件事，别的基本是常数：

| 环节 | 成本 | 说明 |
|---|---|---|
| Groovy 编译 | 约 11 ms / 新脚本 | 缓存命中后接近 0 |
| 事务包装 + 审计写入 | 亚毫秒级 | 审计走独立连接，不参与业务事务 |
| 行数守卫（`GuardedDataSource`） | 每次 `executeUpdate` 多一次计数 | 动态代理实现，不改 SQL 语义 |

所以用 Harken 跑一条 SQL 和直接写代码跑同一条 SQL，差距在毫秒级，换来的是回滚、审计、
行数闸和 AI 只读通道。改生产数据时，这个代价基本可以忽略。

## 5. 没有测的部分

下面这些没有测。

- **并发吞吐**：没有压测。Harken 面向的是人和少量 AI 客户端的低频操作，不是高 QPS 网关。
  并发表现取决于你的业务 Bean 和数据库，不取决于 Harken。
- **长时间稳定性**：只做了 1000 次执行的短跑，没有 24 小时浸泡。Metaspace 收敛是短跑结论，
  长期仍需观察。
- **不同 JVM 的差异**：只在 JDK 17 上测了性能。JDK 21 / 25 只验证了功能正确性
  （`scripts/jdk-matrix.sh`），没做性能对比。换 JDK 的收益应该用你自己的业务脚本去测。
